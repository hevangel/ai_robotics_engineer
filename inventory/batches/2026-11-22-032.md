# Photo import batch 032 — 2026-11-22 (backfill of the 159 missing photo binaries)

No new photographs of hardware and no new inventory records. This batch stores the binaries for the 159 intake photos (`P-20261122-001` … `P-20261122-159`) that batches 001–024 had logged as `not_stored`, so **all 192 intake photos now have binaries in the repo** and the root `index.html` viewer shows a real image for every record that has photos.

## Source and handling

- The owner supplied the photos as a ZIP package built with Codex (`ai_robotics_photo_import_001-159.zip`), containing the 159 JPEGs already named by photo ID, a `photo_map.csv` / `photo_map.json` with SHA-256 checksums, and a bundled Python importer script.
- The package tripped an automated security check because of the bundled executable content. With the owner's explicit go-ahead ("Ignore the bundle script, you wire it by hand"), **the bundled script was never run**; the import was wired by hand with the same tooling as earlier batches.

## Verification before import

- All 159 files' SHA-256 hashes and byte sizes match `photo_map.csv` exactly; every file is a valid JPEG; none carries EXIF metadata.
- The map's original filenames match the filenames recorded in the existing intake text for 149 of 159 photos. The 10 exceptions are batch 010's photos (`P-20261122-050` … `059`), whose intake entries never recorded an attachment filename — those were verified visually instead.
- Visual spot-checks against the intake descriptions passed: `P-20261122-001` (transparent 4WD chassis, HW-0011), `P-20261122-050` (micro:bit GO box), `P-20261122-055` (Waveshare ESP32-S3-Touch-AMOLED-1.75-B carton, SKU 31262), and `P-20261122-113` (the two pouch cells HW-0123/HW-0124).
- After copying, the in-repo files were re-hashed: all 159 still match the package map.

## Changes

- `photos/2026/11/P-20261122-001.jpg` … `P-20261122-159.jpg` added.
- `intake/photos.json`: the 159 entries now have `file` set and `asset_status: stored`. Clauses in their notes that said the binary was not stored/committed were removed (83 notes), and each note gained a uniform sentence recording this import and its checksum verification.
- One identification improved as a side effect: with `P-20261122-113` stored, HW-0124's cell code is now clearly legible — its model is confirmed as **1ICP4/43/55** (was "partially legible; unverified") and its identification confidence rises to high. The barcode sticker number visible in the same photo was deliberately not recorded (serial-number policy).
- `photos/manifest.md` was not touched: it has been stale since the early batches and the established convention is that `intake/photos.json` is the source of truth.

## Follow-up (2026-11-22, owner decision)

After the backfill, the owner reviewed the photo-less records. Of the nine, seven are reported-but-never-photographed items and HW-0069 is a board inside a sealed retail box (correctly unlinked). For **HW-0070** (the Zynq-7020 FPGA module installed on the piSmasher HW-0068), the owner decided to link the assembly photo `P-20261122-059` to the module record as well, since the module is visible mounted on the carrier. Both records' cross-references and notes were updated; records associated with photographs rises to 212.
